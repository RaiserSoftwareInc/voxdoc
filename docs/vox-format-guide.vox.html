Vox Format Guide

Vox is an AI-first, accessible, open document format. Documents are JSON files composed of typed blocks. AI authors them via MCP tools. Humans review by exception. The compiler produces self-contained, responsive, WCAG 2.1 AA compliant HTML.

ℹ️ Who is this for?
This document is written for AI agents that will author Vox documents. If you're an AI reading this — this is your reference.

How It Works

  1. 1
    AI connects via MCP

    Run vox mcp serve document.vox to start the MCP server. AI connects and sees 21 tools for reading, writing, reviewing, and compiling the document.

  2. 2
    AI builds the document block by block

    Call add_block() with a type and content fields. Each block gets a unique blk_ prefixed ID. Build the document sequentially — headings, paragraphs, callouts, tables, diagrams, code blocks.

  3. 3
    AI self-reviews and flags uncertain blocks

    Assign a review.confidence score (0-1) to each block. Blocks ≥0.90 are pre-approved. Blocks <0.70 are flagged with a reason explaining the uncertainty. Set document status to pending_review.

  4. 4
    Human reviews only flagged blocks

    The viewer shows only flagged/pending blocks. Humans approve, flag with a comment, or pass. They never edit content directly — they instruct AI via comments.

  5. 5
    Compile and ship

    Call compile('html') to produce a single self-contained HTML file. If zero blocks were flagged, this happens automatically — no human intervention needed.

Document Structure

A .vox file is JSON with two top-level keys: meta (document metadata) and blocks (content array). Every block has a unique id and a type.

example.vox
{
  "$schema": "https://voxformat.dev/schema/v1.json",
  "meta": {
    "id": "uuid",
    "title": "Document Title",
    "status": "draft",
    "variables": { "version": "2.0" },
    "accessibility": { "language": "en", "reading_level": "technical" }
  },
  "blocks": [
    { "id": "blk_001", "type": "heading", "level": 1, "content": "Hello" },
    { "id": "blk_002", "type": "paragraph", "content": "Version {{version}}" }
  ]
}

Accessibility Requirements

🚨 Compilation will fail without these
Every image needs alt. Every diagram needs description. Every table needs summary. Every math needs spoken. Every handwriting with confidence < 0.70 needs verified transcription. These are not optional — the compiler enforces them.

When authoring as an AI agent, always generate accessibility fields at creation time. Don't add blocks without them and fix later — add them in the same add_block() call. The description field on diagrams should describe what the diagram shows in plain language, not repeat the diagram syntax.

Variables

Define variables in meta.variables or via variable_def blocks. Reference them as {{variable_name}} in any block content. Variables are resolved at compile time. Use them for version numbers, URLs, product names — anything that appears in multiple places.

"variables": {
  "api_version": "v2",
  "base_url": "https://api.example.com"
}

// In block content:
"content": "Send requests to {{base_url}}/{{api_version}}/users"

Review Workflow

After generating all blocks, assign a confidence score to each. This tells the human reviewer which blocks to focus on.

How confidence scores map to review statuses and whether the human reviewer sees the block by default

ConfidenceStatusHuman sees it?
≥ 0.90pre_approvedNo (unless full review mode)
0.70 – 0.89pendingYes, can approve quickly
< 0.70flaggedYes, with AI's reasoning shown
{
  "id": "blk_042",
  "type": "diagram",
  "content": "...",
  "description": "...",
  "review": {
    "confidence": 0.65,
    "reason": "Inferred from code comments — not explicitly documented",
    "status": "flagged"
  }
}

MCP Tools Reference

When connected via vox mcp serve, the following tools are available. Call get_schema() first to learn the full block type schema.

get_document()         → full document JSON
list_blocks()          → block summaries (id, type, preview, status)
get_block(id)          → single block
get_schema()           → full JSONSchema
search_blocks(query)   → blocks matching query
add_block(type, content, after?)  → insert block, returns id
edit_block(id, content)           → update block fields
delete_block(id)                  → remove block
move_block(id, after?)            → reorder
set_metadata(key, value)          → update meta fields
set_variable(key, value)          → add/update variable
add_comment(block_id, comment)    → attach feedback
list_comments()                   → pending comments
resolve_comment(comment_id)       → mark addressed
set_block_status(id, status)      → set review status
set_status(status)                → set document status
validate()        → check against schema + accessibility
compile(format)   → compile to HTML

Example: AI Authoring Workflow

1. get_schema()                    → learn available block types
2. add_block("heading", { level: 1, content: "API Docs" })
3. add_block("paragraph", { content: "Authentication reference..." })
4. add_block("table", {
     headers: ["Method", "Path"],
     rows: [["GET", "/users"]],
     summary: "API endpoint listing"
   })
5. add_block("diagram", {
     syntax: "mermaid",
     content: "flowchart LR\n  A-->B",
     description: "Request flow from client to server"
   })
6. set_variable("api_version", "v2")
7. set_block_status("blk_...", "pre_approved")  // high confidence
8. set_block_status("blk_...", "flagged")       // low confidence
9. set_status("pending_review")
10. compile("html")                              // if zero flags

Principles for AI Authors

  1. Always include accessibility fields — alt, description, summary, spoken — at block creation time, not as an afterthought.
  2. Use variables for anything repeated — version numbers, URLs, product names. One source of truth.
  3. Be honest about confidence — flag blocks you inferred rather than directly observed. Humans trust AI more when it admits uncertainty.
  4. Description fields describe meaning, not syntax — "Authentication flow showing token exchange between client and server" not "Mermaid diagram with arrows from A to B."
  5. One concept per block — don't cram a paragraph, a table, and a callout into a single block. Use multiple blocks.
  6. Use the right block type — a warning is a callout, not a bold paragraph. Steps are a steps block, not a numbered list. The type carries semantic meaning.
